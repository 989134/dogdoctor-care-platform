# 可操作照護網頁與設備串接

## 更新：第二聯絡人逾時後通報 119

流程已擴充為：偵測異常 → 呼叫長者 → 通知照護者 → 人工確認 → 第二聯絡人 → 第二聯絡人通知後 **10 分鐘未接手，通報緊急救護專線 119**。119 為使用者確認的台灣救護專線，參考 [消防署說明](https://www.nfa.gov.tw/cht/?code=list&ids=66)。

第二次倒數從通知服務回報送達、指定帳號站內通知顯示、或裝置顯示推播的時間開始，不能把寄信排隊當作已送達。接手會停止倒數；期限到達僅建立一次 `medical` 指令，通知失敗不會顯示通報成功。狀態保存於資料庫，重啟後繼續處理。既有事件不會憑空補造送達時間。

在設定頁填寫救護專線、**照護現場地址**與**回撥電話**。目前尚未接上真實電話系統，因此不能自動打通 119。頁面有 `tel:119` 撥號入口，僅開啟裝置撥號程式；桌面裝置可能沒有電話功能。按此入口不會把事件改成已通報，必須實際接通後填寫通報結果。測試不會撥打真實救護電話。

電話轉接程式須使用獨立的 `GUARDIAN_MEDICAL_TOKEN`，透過 `GET /api/integration/commands/medical` 取件；payload 含專線、地址、回撥電話與事件摘要。`missing_configuration` 非空時不得撥號，先補齊必要資料。轉接程式需以指令 ID 持久去重，對不確定是否已接通的要求不可盲目重撥。此專案不包含電信帳號、電話硬體或已完成的 119 電信轉接器。

實際接通並完成通報後，回呼 `POST /api/integration/commands/medical/<id>/result`，送出 `{"result":"delivered","detail":"接通時間、通報結果"}`；未接通或無法執行則使用 `failed`。回報 `delivered` 代表完成通報，不能用於僅開始撥號、響鈴或請求進入佇列。網頁仍不宣稱救護車已派遣，也不自動結案。未設定電話轉接器時保留待通報狀態，提供人工撥號與記錄。

藥品辨識新增「開啟相機拍攝」與「上傳裝置照片」。相機需瀏覽器授權，支援 localhost／HTTPS；沒有即時鏡頭 API 時會提供裝置拍照選擇。拍攝後先預覽，再手動送出；關閉、切換頁面或頁面隱藏時停止鏡頭。鏡頭測試使用模擬裝置，實際硬體相容性需在使用者裝置驗收。

使用 `啟動照護網頁.ps1` 或 `..\.venv-test\Scripts\python.exe run_guardian.py` 啟動 http://127.0.0.1:5006 。這個入口使用 `guardian_data` 永久儲存帳號、藥品、事件流程、通知佇列與時間軸，不會建立示範帳號或示範事件。

首次登入：從 `guardian_data/setup-token.txt` 複製設定碼到登入頁，自訂帳號及至少 12 字元密碼；建立後設定碼即刪除。請使用自己的密碼，勿使用 Demo 密碼。

## 處理流程

1. 設備回報異常 → 建立「等待機器狗呼叫」及呼叫指令。
2. 設備確認開始呼叫 →「機器狗呼叫中」。頁面不會代替硬體假裝播放聲音。
3. 設備回報 `no_response`、`abnormal` 或呼叫失敗 → 排入第一聯絡人通知。正常回應則記錄設備回報正常。
4. App 裝置回報已顯示推播、簡訊電信服務回報送達，或指定聯絡人的站內通知實際顯示後，開始 **600 秒**未回應計時。只進入推播／簡訊服務佇列不會開始倒數；送達不代表已讀或接手。
5. 照護者按「接手確認」停止未回應倒數，接著填寫依據，選擇「確認無異常並結案」或「確認有異常，通知第二聯絡人」。僅打開頁面不算接手。
6. 人工確認有異常，或通知後 10 分鐘未接手 →「緊急待處理」，建立第二聯絡人通知。即使第二封通知已送出，仍保持緊急待處理。
7. 有人按「接手後續處理」並填寫實際行動 → 處理中；填寫結果才可結案。

計時由伺服器背景程序執行，約每秒檢查一次，不依賴網頁保持開啟。電腦與服務仍須保持運作；休眠或停機期間無法發送通知，恢復後會處理已逾時事件。所有時間由伺服器記錄，重新整理不重算。部署目前為單一服務程序；不應同時啟動多份背景處理程序。

## 實際通知設定

目前使用 **App Web Push＋簡訊同步通知**，聯絡人使用不同 App 帳號與手機號碼。Email 已移除，舊 SMTP 設定不再寄信。完整手機安裝、HTTPS 與簡訊設定請見 [手機App與通知設定.md](手機App與通知設定.md)。

推播與簡訊各自保存傳送紀錄，獨立工作程序避免互相阻塞。第一個送達回報開始倒數，另一管道回報不重設倒數。通知點擊只開啟事件頁，不會代替人接手。已接手或升級後，尚未送出的舊通知停止，已送出的通知仍可更新送達狀態。

尚未提供真實機器狗語音程式、HTTPS 網址與簡訊服務憑證，因此尚未完成真實手機與設備的端到端驗收。既有事件不捏造過去的呼叫／通知紀錄。

## 機器狗 API 契約

伺服器啟動前設定 `GUARDIAN_ROBOT_TOKEN`；設備要求均附上 `Authorization: Bearer <token>`。請用隨機高強度密鑰，不要放在前端。跨機器連線應透過 HTTPS 或可信任的私人網路，不能直接公開本機 HTTP 服務。

### 1. 回報偵測

`POST /api/integration/events`

```json
{"event_id":"device-event-unique-id","kind":"fall","risk":"high"}
```

kind 可為 `fall`、`inactivity`、`abnormal`。同一偵測重試必须使用同一 event_id，避免重複通知。回傳事件 ID 會加上 `robot:`。

### 2. 取出呼叫指令

`GET /api/integration/commands/robot`

回傳 commands，包含 id、event、kind、status。設備應依指令 id 去重，實際播放呼叫語音並取得回應；尚未完成的指令會重複出現在輪詢結果，不可每次輪詢都重新播放。回應異常的判斷與呼叫等待時間由設備語音模組實作，本網頁不使用 Gemini 猜測長者狀況。

### 3. 回報開始與結果

`POST /api/integration/commands/robot/<command-id>/result`

```json
{"result":"started","detail":"設備開始播放呼叫"}
```

之後回報 `normal`、`no_response` 或 `abnormal`，detail 填寫必要回應摘要；不可傳入不必要的個人資訊。呼叫未能執行時回報 `failed`，會轉為通知照護者，明確標記呼叫失敗。設備未回報時保留等待狀態，不會冒稱已取得語音。

## 外部通知服務（選用）

若改用其他外部通知轉接服務，啟動前設定 `GUARDIAN_NOTIFY_TOKEN`，由受信任的轉接程式使用該 Bearer token：

- `GET /api/integration/commands/notify`：第一聯絡人通知。
- `GET /api/integration/commands/next_step`：第二聯絡人通知。
- `POST /api/integration/commands/<kind>/<id>/result`：回傳 `{"result":"delivered","detail":"管道與送達確認"}` 或 `failed`。

接收者由該通知服務的設定管理。不要同時啟用內建 App 推播＋簡訊與輪詢同一種指令的外部服務，以免重複寄送；本介面為至少一次取件，轉接程式必須以指令 id 去重。通知第一聯絡人的回報僅能啟動一次倒數；第二聯絡人通知不會自動結案。
